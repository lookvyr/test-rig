## Confirmed and appropriately scoped findings

### P2, high confidence: stale missed-run rescheduling overwrites a concurrent schedule edit

`apps/server/src/scheduledTasks/ScheduledTaskService.ts:599-622` computes the replacement due time from the originally loaded task and updates by task ID alone. `:624-643` reads a complete due batch and processes it sequentially; an earlier dispatch can wait on worktree setup or an ongoing thread launch while the UI edits a later missed fixed-time task. Upsert correctly calculates a new due time (`:745-770`), but the stale missed-run branch then replaces that due time with the old fixed-time schedule's next occurrence. Unlike `runTask` (`:479-501`), this branch neither rechecks the row nor guards the UPDATE against its original next_run_at/schedule/enabled state.

I independently reran the archived deterministic Deferred/TestClock reproduction at `/private/tmp/testrig-audit-schedule-race.test.ts`. With `TZ=UTC node_modules/.bin/vp test run apps/server/src/scheduledTasks/ScheduledTaskAuditReview.test.ts`, the final assertion failed: an interval task whose new due time was `2026-10-06T12:02:00.000Z` instead had `2026-10-07T11:00:00.000Z`; its stored schedule was still the new interval. UTC was used so the seeded 11:00 fixed-time slot matched the initial due timestamp. The same test also failed in the local zone, but the UTC result avoids artificial timezone ambiguity in the fixture. The temporary checkout test was removed.

This is a concrete scheduler bug, not the intentional policy of skipping late fixed-time runs. A guarded stale-snapshot update or fresh reread/reclassification should preserve concurrent edits and recreated rows.

### P2, high source confidence: fresh Claude native-session fallback incorrectly tries to resume the new native ID

`ProviderTurnStartService.ts:626-667` falls back from a failed resume or uncertain history delivery to `ensureThread` with a cleared native ref while preserving the durable provider-thread identity. `ClaudeAdapterV2.ts:6884-6895` decides resume from `providerTurnOrdinal > 1`, which counts the durable provider thread's old native turns. The fresh ID has not yet been created, so it can be sent as SDK `resume` instead of `sessionId`. This is reachable through the production resume-fallback path after an older completed turn; it is not a theoretical mismatch in an unused interface.

Upstream `efecd3cf8` threads `nativeThreadHasTurns` through ProviderTurnStartService, RunExecutionService and ProviderAdapter, with native and legacy fallback integration tests. It fits the retained Claude product. Adapt the change while preserving Test Rig's additional `providerThread.forkedFrom !== null` resume condition at `ClaudeAdapterV2.ts:6895`; a direct replacement of upstream lines would lose that fork handling. No live Claude validation was performed here.

### P2, high confidence: commit-message preparation changes the real Git index before provider generation succeeds

`GitVcsDriverCore.ts:2082-2096` resets/stages the actual index in `prepareCommitContext`. `GitManager.ts:1871` invokes that preparation before style-policy reads and provider generation (`:1888-1900`). If generation fails or the action is interrupted, the workflow exits before commit yet the user's previous partial staging has already been replaced. Preparing a selected-file commit can unstage unrelated work; preparing all changes can stage work previously left unstaged.

Upstream `4ee6bfd50` prepares the prompt against a temporary index and stages the real index only immediately before commit. The fix also handles split indexes and avoids reset changing merge state when preparing a selected-file temporary index. This is retained Git functionality; there is no fork policy supporting the destructive preparation side effect. Static source review independently confirms the exact order and mutation. Do not describe this as deleting working files or losing file contents; the confirmed effect is altered staging state.

### P2, high source confidence: Stop cannot repair a projected running run after its session or terminal write is lost

`Orchestrator.ts:8038-8061` rejects Stop when its selected running provider turn has no active session. The local `settleOnly` route (`:8008-8015`) requires the provider turn to already be non-running. The successful-interrupt follow-up `dispatchBackgroundWorkSettle` (`:7747-7755`) returns while any run is still preparing/starting/running, including the stopped target itself, so it cannot terminalize a target whose final provider write was lost. These facts independently support the runtime agent's deterministic missing-session reproduction reported in `/private/tmp/testrig-audit-runtime.md`.

Upstream `a7a2230c3` adds repair of the owning run/attempt/nodes/requests/messages and guards late finalization/checkpoint effects. This is valuable adapted intake. Keep the user's accepted run-scoped late Stop behavior, and keep app-owned children running as documented in `docs/user/delegated-agents.md:59-65`. Neither of those policies excuses the stale-running root. Avoid blanket claims that ordinary Stop fails; normal terminal ingestion and restart recovery are implemented. The issue concerns terminal-persistence/process-loss recovery. P1 can be justified only if the overall report's prioritization treats this recoverability gap as urgent; source alone does not establish a common incidence rate.

### P2 foundation defect, high confidence; narrow production impact: DrainableWorker stops after an item fails

`packages/shared/src/DrainableWorker.ts:47-55` runs processing inside `Effect.forever` without containing an item's cause. A failure ends the worker; later queued items remain outstanding and drain cannot finish. I independently ran `node /private/tmp/testrig-runtime-worker-repro.mjs`, yielding `{"workerExit":"Failure","processed":[],"drainResolved":false}`. It waits on the actual worker fiber's exit and uses no timing sleeps.

Upstream `24e4b62c8` is a coherent foundation fix with failure/defect/self-interruption/queue-shutdown tests. However, do not infer that ordinary PR/settlement DB errors currently kill these V2 workers: `ThreadPullRequestService.ts:355-364`, `ThreadSettlementService.ts:502-517` and `PullRequestSyncReactor.ts:332-338` catch non-interruption causes. They propagate pure interruption, so self-interruption is still relevant. `WorktreeCleanup.ts:274-306` catches typed errors only, leaving defects capable of killing its worker; production-triggered defects were not demonstrated. The report should retain the helper bug and intake recommendation while downgrading any blanket P1 runtime outage wording.

### P2, high confidence: declared MCP tool failures are exposed as successful results by the pinned Effect runtime

Current toolkit declarations use `failureMode: "return"`, for example `mcp/toolkits/worktree/tools.ts:24-30`, and production registrations go through `McpServer.toolkit` (`McpHttpServer.ts:245-280`). The resolved Effect `4.0.0-rc.115` `src/unstable/ai/McpServer.ts:1573-1585` unconditionally constructs `CallToolResult` with `isError:false` from `result.encodedResult`; it does not inspect the encoded result's declared-failure state. Its outputSchema is generated from the success schema (`:1546-1549`). A returned failure object is consequently marked successful and can violate the advertised structured success schema.

This independently supports the workspace agent's reported production registration reproduction returning a capability-denied object with `isError:false`. Capability enforcement itself still rejects the action; the bug is response semantics and compatibility, not a bypass. Upstream `dff412c34` adds regression assertions and an SDK test dependency only, so cherry-picking it alone does not fix the pinned runtime. The runtime/library repair or a narrow adapted registration fix must accompany the test. No external MCP client was launched here.

## Challenges and downgrades

- **Inherited subagent PR associations: insufficient evidence for a bug.** `SubagentProjection.ts:54` copies parent associations, links and branch metadata for native and app-owned children. That is real, but the children intentionally share the parent's checkout and project. The current link contract contains reference metadata, not parent run/node ownership IDs that automatically become invalid. A copied explicit link or unlink choice can reasonably represent the shared work. There is no documented opposite policy in FORK.md or delegated-agent docs. It may deserve an explicit product decision or a concrete stale-association reproduction, but do not classify copying alone as a confirmed defect or blindly clear shared PR associations.
- **Fast normalization: separate, lower confidence behavioral issue.** `claudeModelOptions.ts:39-47` omits fastMode when the selection has no boolean; upstream `efecd3cf8` makes supported unset Fast explicitly false. Source confirms the difference but this review did not inspect a live harness's ambient settings/defaulting behavior. Present it as an adaptation candidate/default guarantee gap unless the providers report supplies concrete inherited-settings evidence. It is separate from the high-confidence native-session fallback failure.
- **Parent Stop not recursively cancelling app-owned children is accepted behavior.** The explicit current documentation says children are separate conversations and can continue. Upstream thread.stop/delegated cancellation broadening is a policy change, not proof of a regression. Test Rig's late Stop must remain run-scoped.
- **Missing ProviderTurnStartMemory fixture and OpenCode transcripts:** treat the provider agent's reproduced ENOENT results as validation/packaging gaps; they do not by themselves demonstrate a production provider failure. This review did not rerun those tests. Restoring the fixtures is appropriate retained test coverage, independent of live-provider acceptance.

## Additional transport and SQLite review

### P2, high confidence: an RPC handler defect ends unrelated active requests

I independently ran `/private/tmp/testrig-runtime-rpc-repro.mjs` with the installed runtime. Default options returned `{"first":1,"boomExit":"Failure","next":"subscription ended"}`. Running with `AUDIT_DISABLE_FATAL=true` returned `{"first":1,"boomExit":"Failure","next":2}`. The program starts a subscription, waits for its first event, makes another handler die, then races the subscription's actual fiber exit against its next event; no sleeps or timed polling.

Production `ws.ts:1407-1409` constructs `RpcServer.toHttpEffectWebsocket` with `disableTracing:true` but no `disableFatalDefects`. Effect rc115 `RpcServer.ts:301-305` therefore sends a connection-level Defect for a handler defect, instead of a failure Exit attached to the request ID. Upstream `8ddf200e8` changes the server option and supplies coverage. This is a retained multiplexed WebSocket robustness bug. Its incidence requires an actual handler defect, so ordinary typed request rejections should not be described as disconnecting the client.

### P2 adaptation candidate, high source confidence: cancelling a full-buffer stream can strand the shared socket reader

Upstream `eac52f008` shuts down a cancelled stream entry's bounded queue before sending its interrupt. The current patch and installed rc115 RpcClient stream finalizer remove the entry and sendInterrupt without Queue.shutdown. A shared protocol reader already blocked offering a chunk to that full queue is consequently not released merely by removing the entry. Upstream's focused `RpcSessionFactory` regression deliberately blocks a consumer, sends a 64-event chunk, cancels it, then checks a probe on the same socket. This is a reachable shared-client transport concern independent of hosted/cloud features. This review examined the precise missing finalizer and upstream test; it did not independently run the full socket reproduction. Port the runtime patch and focused regression together.

### P2 robustness candidate, medium production reachability confidence: SQLite write lock is deferred and Node error codes are misclassified

Both `apps/server/src/persistence/NodeSqliteClient.ts:277-285` and `packages/shared/src/nodeSqliteClient.ts:272-280` omit beginTransaction, so installed Effect SQL uses `BEGIN`. Each adapter serializes its own connection through a semaphore. Upstream `0fe4fa40f` selects `BEGIN IMMEDIATE` for writable connections to acquire the write lock before a read snapshot, and maps Node SQLite's errcode to errno for proper classification.

The SQLite failure is valid when another writer connection/process changes the database after this transaction's read: a later write can get SQLITE_BUSY_SNAPSHOT that busy_timeout cannot fix. It should not be described as a race between ordinary parallel effects on the same SQL client, since its semaphore already serializes those. Production V2 imports the server-local duplicate adapter (`persistence/Layers/V2Sqlite.ts:6,28`), so porting only shared/nodeSqliteClient would not repair that path. This review did not establish a normal supported two-writer deployment or run a cross-process lock reproduction. Keep the missing upstream lock/classification repair as a robustness intake item and state the exposure condition instead of overclaiming common production failures.

## Final challenge of earlier recovery and history findings

### P2, high confidence: parent recovery prematurely cancels durable app-owned delegated task records

The archived `/private/tmp/testrig-runtime-delegated-recovery-repro.test.ts` uses partial mocked projection entities, so its assertions alone should not be mistaken for a full persisted workflow. Source tracing nevertheless validates its relevant data and reachability. `Orchestrator.ts:6268-6288` produces a running subagent with `origin:"app_owned"` and a durable childThreadId; `:6310-6330` produces the corresponding running task item with the same ownership and parent run/node references. The child has an independent thread/run. A completed parent with an unfinished child is supported by the documented delegation/Stop behavior, not an impossible state. The recovery query loads unfinished task items and their linked nodes/subagents even when their parent run is already completed (`ProjectionStore.ts:3857-3863,3889-3900,3914-3918,4010-4020`). Thus the repro's running-parent and completed-parent examples model reachable producer data.

`ProviderRuntimeRecoveryService.ts:332-367` cancels all matching open nodes/subagents for recovered nonterminal runs; `:403-422` cancels their task items; `:432-511` cancels open background-capable items/entities on settled runs. None of these paths excludes app_owned tasks with independent child ownership. Parent recovery can therefore set the durable delegation record to cancelled and record a lost-work note before child recovery/completion determines its real result. The intended fix from upstream `5108c978b` adds exactly those ownership exclusions; the broader commit already has partially represented Test Rig fixes, so do not call the entire commit absent.

Severity should remain P2 for incorrect parent task state and recovery notes. This is distinct from the accepted policy that user Stop leaves children running: preserving independent task ownership is consistent with that policy. Do not claim the reproduction proves the child's process was killed, its files were lost, duplicate delivery occurred, or its eventual result can never arrive. In fact, `Orchestrator.finalizeAppOwnedSubagent` (`:8411-8418,8441-8446`) can later replace the cancelled parent task status from the child's true terminal state; this review did not execute the full resumed-child sequence. Adapt ownership exclusions with terminal-child reconciliation and current wake/user-precedence rules.

### P2, high confidence: agent-only child transcripts incorrectly bypass item/byte paging budgets

The `/private/tmp/testrig-runtime-agent-history-repro.test.ts` fixture's agent-created user_message/turn_start is directly produced by `SubagentProjection.ts:136-145`. Native children can have a runless prompt followed by commands; the test's null run IDs are therefore plausible. App-owned child message dispatch also uses agent-created task prompts. Ninety command rows are a reasonable large-child transcript, rather than an impossible object arrangement.

`threadHistoryPaging.ts:189-199` switches from item/byte limits to complete-turn handling whenever it sees _any_ turn_start, but only human user turns increment userTurns (`:205`). A single agent-created turn thus admits all ninety command rows, matching the runtime agent's observed 91 rows instead of maxItems=75. SQL exhibits the same bug: `turn_anchors` includes agent messages (`ProjectionStore.ts:2692-2699`), `user_anchors` filters human messages, but selected's unlimited LIMIT tests the count of all turn anchors (`:2712,2721`) rather than human anchors. The local inheritance fallback (`:3215`) and memory implementation need the corresponding fix.

This is a resource/paging failure, not demonstrated transcript deletion. The raw-turn ceiling limits the number of agent turns but does not limit rows within one such turn. It is also separate from the documented deliberate large _human user_ complete-turn exception. Upstream `88744f3dd` makes that distinction in all owning paging paths. No rerun was necessary after the producer/query review; the archive records the runtime agent's focused failing assertion.
