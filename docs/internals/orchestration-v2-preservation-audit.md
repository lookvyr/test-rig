## Replay preservation and repair proof

The original `b01026c6` outcome was ordered, repeatable replay with bounded pages that release consumed objects. Limiting each SQL query alone does not prove that earlier pages are released.

The active V2 `Layers/OrchestrationEventStore.ts` preserves `Stream.paginate` for agent reads and command replay, with 500-row pages and normalized total limits. `EventStore.readByCommandId` delegates to that reader. FoundationPersistence verifies 1,001 matching command events mixed with unrelated/project/V1 events, exact-page and empty results, page limits, and a duplicate command returning the same ordered events. Projection rebuild applies 1,005 events one 500-row page at a time and preserves the previous projection when the next page fails.

The active `EventSink.catchUp` instead concatenated recursive 256-row streams. A temporary probe using the original fork's `v8.queryObjects` marker technique reproduced retention at the second page: two page markers remained alive where only the current page should remain. The repair replaces recursive concatenation with cursor-only `Stream.paginate`. It retains the same page size, high-water boundary, thread/event filters, event order and replay-to-live subscription sequence. The temporary probe was removed; the permanent FoundationPersistence regression consumes 1,025 events and checks both sequence and live page-marker count at each boundary. No whole-history collection was added.
