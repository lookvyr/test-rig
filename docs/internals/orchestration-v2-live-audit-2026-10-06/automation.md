## Concrete retained-scope UX gaps

### A1 — P2: Bound task automation controls exist only in Settings

Local `apps/web/src/components/chat/ThreadDetailsPanel.tsx:61-142` has Workspace and Version Control sections and no automation subscription/control. Nightly imports `ThreadAutomationsPanel` at `ThreadDetailsPanel.tsx:29` and renders it at `:226`. The upstream panel filters `scheduledTasksLive` by `task.threadId` (`ThreadAutomationsPanel.tsx:44-63`), shows schedule/next run/status (`:145-177`), and exposes Edit/Run now/Pause/Resume/manage (`:108-132,179-215`). It also keeps a failed subscription visible rather than making load failure look like no automations (`:65-68,134-138`).

Local Settings already has matching partial-enable/run/delete RPC controls (`ScheduledTasksSettings.tsx:393-416`) and task deep-link parsing/open-on-load (`scheduledTasksSettings.logic.ts:18-28`, `ScheduledTasksSettings.tsx:324-330`). This is a narrowly missing chat entry point, not missing scheduling backend. Port the upstream section using local scopedThreadRef props and retained interval/fixed-time types. The upstream webhook-specific Run-now guard should not drag webhook contracts into the fork.

### A2 — P2: Custom snooze has a shared resolver but no UI

Nightly's common menu adds `snooze:custom` (`threadActionMenu.logic.ts:152`); the modal lives in `CustomSnoozeDialog.tsx:39-220`, is mounted in both root branches (`routes/__root.tsx:184,239`), and handles header + sidebar row + hover/bulk entrances (`hooks/useThreadActionMenu.ts:163`; `Sidebar.tsx:597,4237,4502`). Local menu maps presets only (`threadActionMenu.logic.ts:79-88`), and both local header/SidebarV2 dispatch assume the ID resolves to a preset (`hooks/useThreadActionMenu.ts:145-150`; `SidebarV2.tsx:2427-2429,2646-2648`).

Local shared `packages/client-runtime/src/state/threadSettled.ts:287-315` already contains CustomSnoozeInput and resolveCustomSnooze (date/time and duration, future/invalid/DST validation). No CustomSnoozeDialog file/host exists. Port the upstream modal and all snooze entrances rather than adding only one menu option.

### A3 — P2: Per-thread auto-settle choice is unreachable

Nightly has `Auto-settle behavior` with checked Enabled/Disabled options (`threadActionMenu.logic.ts:185-202`). Local menu's state and union omit auto-settle (`threadActionMenu.logic.ts:9-44`) and common header dispatcher has no handler. Local already has `thread.auto-settle.set` contract (`packages/contracts/src/orchestrationV2.ts:2572`), runtime command (`operations/commands.ts:451-464`, `state/threadCommands.ts:224`), optimistic state (`state/threadCommands.ts:435`), and server handling (`Orchestrator.ts:2692-2698`). Server settlement explicitly skips opted-out threads (`ThreadSettlementService.ts:139`), and projection queries retain the opt-out (`ProjectionStore.ts:5128,5644`). Global Settings → Auto-settle inactive threads is a different choice and cannot replace a per-thread opt-out.

Import upstream menu/state/gating and both header/sidebar dispatch. Keep deliberate SidebarV2 layout. This is backed backend capability with missing user control, not reason to invent another settlement model.

### A4 — P2: Archive has recovery UI but no way in

Nightly adds `Archive thread`, disabled while provider is attached (`threadActionMenu.logic.ts:224-230`), and routes both header/sidebar actions. Local common menu ends at Delete (`threadActionMenu.logic.ts:105`) and neither header/SidebarV2 menu offers archive. Yet local `useThreadActions.ts:183-243` has archive/unarchive, contract `orchestrationV2.ts:2519,2524` accepts both, and Settings renders Archived threads + Unarchive (`SettingsPanels.tsx:2009-2090`). Server archive owns cancellation and cleanup (`Orchestrator.ts:3108+`).

A user-visible one-way omission remains: historical rows can be restored, but users cannot archive an ordinary chat from its actions. Adapt the upstream menu entry + both handlers and archive-running gating; do not conflate Archive, Settle, Delete.

### A5 — P2: PR watch state and stop action lack a UI

Nightly `ThreadDetailsPrRows.tsx:76-96` reads each linked PR's watch and exposes Stop through `threadEnvironment.watchPullRequest`; `ThreadDetailsPrRow.tsx:354-381` renders the eye and `Stop watching #N` plus explanatory tooltip. Local ThreadDetailsPanel offers only `Pull request details` (`:126-133`); these two nightly PR row components are absent. Search of local web source found no watchPullRequest caller, although runtime command is present (`state/threadCommands.ts:265`; `operations/commands.ts:979-996`), contracts and Orchestrator watch handling persist it (`orchestrationV2.ts:2664`; `Orchestrator.ts:2929-2982`), and timeline summaries say Watching / Stopped watching (`t3ToolSummary.ts:375-381`).

The agent can start an ongoing watch but the human cannot inspect/stop it in the expected thread details place. Adapt the upstream PR watch indicator/stop segment to local linked-PR representation, retaining Test Rig's Link PR entry point and hosting-toggle boundary. Generic link/unlink is not equivalent to explicit stop watching.

## Accepted distinctions and scope limits

- Interval/fixed-time task Settings is present and source-complete for its visible create/edit/pause/manual-run/delete controls. Local `docs/internals/scheduled-task-policy.md:5-34` expressly adopts upstream queue, overlap, dispatch status, server timezone, one-minute minimum, awake-server requirement and explicit opt-in. New webhook/relay route/URL/signature/delivery UI is excluded. Earlier deterministic missed-fixed-time rescheduling race remains valid in `coordination.md:F1` but is not a new UI finding here.
- Local task editor adds no-project launches, Permissions, original branch preservation (`scheduledTasksSettings.logic.ts:132-153`) and saved/project permission defaults (`:157-167`); its explanatory dispatch-status/server-timezone text is more explicit than nightly. These are selected extensions/corrections and should stay.
- Nightly schedules use selected Settings scope (`ScheduledTasksSettings.tsx:240,337,783`); local uses all environments (`:221-242,277`) with per-environment grouping and no scope provider. Local Settings has separate ProjectSettingsScope rather than upstream global scope. Treat this as part of the broader Settings scope difference, not an isolated scheduler defect.
- Operational recovery is retained despite excluded usage/pricing dashboards. Local UsageLimitRecoveryBanner is backed and independently enables resume/snooze; additionally supplies Resume now after reset and Wake now to undo snooze (`:75-97`). Nightly hides the snooze action after snoozing and always says Resume at reset (`:78-97`). No concrete missing local recovery UX found. OpenCode reliable reset remains unavailable; manual retry is expected.
- Parent Stop does not recursively stop children by chosen policy (`docs/user/delegated-agents.md:60-65`). Main ChatView captures active run ID (`ChatView.logic.ts:147-166`, `ChatView.tsx:2762-2776`), whereas nightly passes only thread ID (`ChatView.tsx:4506-4512`) and has newer thread.stop/cascade behavior. Keep accepted late-Stop identity protection and nonrecursive behavior. Watch-stop UI above is independently useful; this report does not request wholesale cascade port.
- Private request_secret is absent end-to-end (nightly SecretRequestCard, SecretRequests service, secret_request turn item and answer RPC). Its only actual secretRef consumer found in nightly is `ScheduledTaskService.ts:1047-1065` webhook signature save. Current scheduling policy excludes webhooks; absent private secret card therefore is contextual new feature, not a retained-scope blocker. Future independent local-secret consumer could justify a separate adapted port preserving private value handling.
- Pinned rows, settle/unsettle, presets, Wake thread and quota recovery are implemented locally and need live observation rather than source-based claims of failure. Shared web renderer serves desktop as well; no new shell/IPC-specific change is needed for these missing UI entries, but native context menus merit the primary agent's smallest desktop smoke if imported later.
